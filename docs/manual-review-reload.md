# Manual atomic review reload

The restaurant detail page offers a separate full reload action. Ordinary synchronizations and partial-import merge retries retain their existing behavior. The replacement affects only the selected restaurant, retaining its identity, settings, memberships and monitoring preference. The application translates nothing.

## Durable collection and validation

`reload-establishment-reviews` authenticates the user and calls `request_review_reload`. The SQL routine authorizes an owner/admin/manager in the restaurant organization and freezes the account's FR/VI language in a new `initial_import_jobs` row of kind `reload`. The normal durable wake, bounded provider observations, concurrency slots, leases and cron fallback are reused. Closing the app does not stop work. No report generation is enqueued.

Every click carries a persistent UUID. Server intent aliases also cover requests joining or resuming an earlier job. Replaying an intent after completion returns that job; it cannot initiate another paid run. A start reservation without a saved provider identity is blocked. A saved run is observed again, never blindly restarted. An explicit retry after a confirmed incomplete/failed run can create a new job while preserving the consumed attempt. A complete staged batch is retried as a database commit, with no new collection.

Before any destructive work, every native row is checked against the restaurant CID/place ID, the frozen requested language, and a fresh provider timestamp. The worker deduplicates by native review ID and sorts by publication date with stable ID ties. It selects the latest 150, across all ratings, including textless reviews and without an age limit. The completeness target is `min(150, consistent nonnegative native Google total)`. Without a reliable total, only 150 unique dated reviews establish completeness. An empty dataset cannot establish a genuine zero-review restaurant and fails closed. Zero is accepted only with a fresh native place record proving the same identity, requested language and an explicit zero total. Partial, mismatched, stale, undated/future-only, or failed results leave the previous corpus and reports intact.

The service-only `stage_review_reload` independently validates scope, native IDs/originals/translations, completeness, reservation ownership and a confirmed successful native run. Its immutable bundle and summary are SHA-256 bound. FR/VI Google translations are stored exactly as received, alongside the original. A translation for another target language is rejected. The temporary private table is RLS enabled with no client policy; failed terminal stages expire after 24 hours via an hourly, idempotent cleanup. Intent/reservation traces do not expire with it.

Validated stages have a strict 24-hour reuse window. A content-free validation marker survives failure; legacy jobs are recognized by their saved fetched count or persistence timestamp. Both manual enqueue and the worker's staging check reject an expired/deleted validated stage before provider access, and the apply RPC also rejects it. Retry before expiry requeues the same job and commits the same staged payload, retaining run/dataset IDs and request counters. An expired stage requires an explicit subsequent decision; it never silently turns Retry into a provider read or fresh collection.

## Atomic replacement

`apply_review_reload` runs as the service role so it can use the existing invoker ingestion routine. It takes the same restaurant corpus advisory lock as ingestion/freezing, locks the restaurant and job, verifies the lease and stage hash, and invokes a narrowly scoped privileged cleanup. All deletion, insertion, cursor/count updates and completion happen in **one transaction**. Any error rolls back the old reviews, translations, reports and settings. A duplicate apply after completion returns the stored result without deleting again.

Reviewed dependencies: current historical sources, batch tasks/runs and parallel/preparation copies are retired through the existing retention helper; durable report publications, recommendation sheets, weekly/historical report projections, retired report fallback scopes, and scoped isolated experiment content are deleted. Native experimental receipts are first projected to the content-free provider ledger. The existing review FKs remove translations, provider raw data, display texts, reply drafts and review notifications. Review AI accounting is recorded before deletion; display call receipts retain their technical trace with a null review FK. Seen/import keys and obsolete observation/snapshot data for this restaurant are removed. Fresh rows receive new internal IDs and native translations through normal ingestion. Restrictive legacy review FKs fail the transaction rather than bypassing constraints or deleting unrelated content. Retired legacy pipelines remain disabled. There are no application-managed review storage objects in the inspected production inventory; review photo URLs are part of the replaced review rows.

`reviews_attention_rule` distinguishes attention from automatic processing: 1--3-star reviews still require attention; historical rows may keep `requires_ai_analysis=false`, while live rows retain the previous requirement. At 4--5 stars both flags remain false. Reload staging continues to require `historical_import=true` and `requires_ai_analysis=false`. The production insert trigger excludes historical imports, and the automatic `analyze-review` handler independently skips them. No existing row is updated by this constraint correction. Offline reload tests load every production review CHECK plus the real AI enqueue trigger, with HTTP replaced by a recording stub; a live-review positive control proves the stub detects a dispatch. The earlier fixture omitted these CHECKs and used a no-op AI trigger, so it did not catch the contradiction.

Reload is rejected while an import/sync, generation or unknown consumed attempt is outstanding. Generation/experimental guards and the existing sync guard prevent new competing work while queued/running. A successful reload records a timestamp barrier: older ingestion payloads and obsolete publication sources cannot repopulate the removed corpus. Existing replay tombstones, provider reservations, native identities and the provider ledger are retained. The frontend discards cached reports older than the committed replacement.

## UI and operations

The action explains that old reviews/translations will be replaced and dependent reports removed after validation. Failure uses exactly the approved account-localized message and Retry button, without native error details or provider branding. Success shows the available review count and states that a new report can be generated manually. No report is generated automatically.

After a committed replacement, the report observer and its persisted manual intent use a namespace containing that reload's completion timestamp. Retired report request IDs cannot be reused accidentally for the new corpus. The report cache key stays stable; its timestamp barrier rejects old reads. Without a committed reload, existing controller/intent keys are unchanged. A lost-response retry inside the new namespace keeps the same intent, and observing/mounting still never generates a report.

Deploy only `20261028083600_manual_atomic_review_reload.sql`, `process-initial-import-jobs`, `reload-establishment-reviews` (JWT enabled plus `requireUser`) and the normal Pages UI. Deploy the backward-compatible worker from the merged commit before applying the migration; deploy the new endpoint after the migration and verify the Pages assets. Do not invoke reload/import/generation endpoints to validate installation. The migration creates schema/functions/guards and one empty-stage housekeeping cron job; it does not queue work or delete restaurant data.

For installations already containing that migration, apply only `20261028100909_allow_historical_attention_without_auto_ai.sql` for the attention/expiry correction. Existing worker v17 already checks the staged result before accessing the provider and needs no binary change. No job is resumed, payload replaced, or review deleted by that migration. Do not remove this constraint exception while compatible historical rows exist; disabling new requests can use the existing execution-grant rollback without altering consumed attempts.

Offline tests exercise native completeness/duplicates/language/identity, durable intents and double clicks, scoped replacement, translation/raw deletion, preserved receipts/tombstones, rollback restoring an existing report, database-only retry, unknown start protection, source/ingestion fences, access restrictions, FR/VI UI, cache invalidation, and ordinary import regression tests. Simulated fixtures prove these control paths, not live provider coverage. The first paid reload and native dataset coverage remain a deliberate user test.

To stop offering the action, revert the UI or revoke authenticated execution on `public.request_review_reload(uuid,uuid)`. Keep the worker, migration, stage/intent records and guards needed by consumed or running jobs; do not reset their reservations or restore old publications. A committed successful replacement has no automatic content rollback: prior data was intentionally removed. Transactional rollback covers failures before commit.
