# Account language and review display

The account's saved `profiles.preferred_language` selects French or Vietnamese. Ordinary review lists, details and notification excerpts use the original or a verified display translation in that language; English is no longer a display fallback. The original remains available through a localized toggle. Missing, failed and unknown translations show the original with an explicit status. Textless reviews do not need translation. The frozen original and English analysis evidence remain unchanged in audit/report dossiers.

Display translations live in `review_display_texts`, separately from `review_translations` used by the analysis pipeline. Their identity is review UUID, target language and exact UTF-8 SHA-256 of the original (`original_text`, falling back to `text` only when absent). A source change deletes previous display rows. Review deletion cascades to all display content. No ingestion fields, ratings, latest-150 selection, JEV inputs, selector, Sol or report generation are changed.

The reader RPC chooses the language from the authenticated profile, validates every requested review against the existing organization/establishment access model, and handles at most 30 IDs. Visible UI components batch their requests, and poll pending results while mounted/visible. They reject a result for another source revision or language. Switching account/language resets component state and never imports reviews. The general client review query no longer downloads unused provider-English translations.

New text insertions and actual source changes enqueue cheap preparation for languages used by members of that organization. The trigger does no HTTP or model work and cannot block import completion on translation. Existing reviews are not queued during installation. Existing data is prepared only on visible reads; changing account language does not enqueue the entire historical corpus. The minute cron handles preparation independently of an open browser; reads and worker continuation can dispatch promptly using the existing server scheduler credential.

The worker accepts only the existing server scheduler authentication. Globally serialized claims allow two processing reviews at a time. Each invocation handles at most two rounds of two jobs. Provider metadata is normalized, checked for script incompatibility and, on longer FR/VI/EN samples, statistical disagreement with pinned `franc-min@6.2.0`. Statistical detection only flags a verification need; it never overwrites the original language. Missing/inconsistent language is identified in the same direct-from-original OpenAI request as translation, using the existing server `OPENAI_API_KEY` and existing translation model `gpt-5.6-terra`. Low-confidence identification fails honestly. Very short or mixed reviews can remain uncertain; these checks and mocked tests do not establish model translation quality.

A legacy provider translation is reused only when its target, translated text and exact original can all be matched to the saved native provider payload. Legacy rows without source evidence are not certified. At the audit, all 1,109 provider translations were English, so none was a compatible FR/VI display cache entry. Newly generated display translations are reused across users with access. No display translation is written into analysis inputs.

A durable content-free receipt precedes each model POST and prevents another request for the same review/target/hash. Unknown results are never automatically retried. Expired claims before reservation can be recovered. Matching late results can be saved without a second POST; changed or deleted reviews cannot be republished. Even after deletion a matching attempt UUID can record native model/usage while its review pointer is cleared. Original changes remove previous translated content; an already consumed hash that later reappears without its cache is blocked rather than blindly resent. Explicit recovery for unknown/failed consumed attempts is not exposed in this release.

Offline verification executes the migration and actual SQL functions in PGlite with mocked dispatch, plus provider HTTP and UI simulations. It covers FR/VI, EN originals, unknown/inconsistent language, textless reviews, language/account switches, shared cache, provider compatibility, changed/deleted sources, access denial, concurrency, reservations and late/unknown results. No real translation, Apify collection, import or report regeneration is necessary for deployment verification.

Deploy `process-review-display` first, preserving its scheduler check and `verify_jwt=false`, then apply the migration and publish the client. Re-read version/files, RLS/grants, cron and zero initial queue/receipt counts. A safe pause is `update private.review_display_runtime set enabled=false where singleton`; it prevents future claims/dispatch without clearing consumed attempts, changing imports or modifying reports. Existing queued preparation waits until re-enabled.
